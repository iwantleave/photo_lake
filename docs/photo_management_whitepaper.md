# 照片管理白皮书

**副标题：家庭与个人照片资产的目录规范、元数据体系与长期保存方法**

版本 1.0 · 2026-10-04 · 依据 Photo World（photo_lake）v1.3 实现约定编写

---

## 摘要

照片管理失败的原因从来不是「工具不好用」，而是**没有一开始就把文件放对地方**。一旦照片散落在相机卡、手机、聊天记录、U 盘、外置硬盘和某个名为「新建文件夹」的目录里，任何软件都救不回来——因为文件本身没有携带「这是什么、什么时候、和谁在一起」的信息。

本白皮书给出一套**两级目录 + 元数据索引**的方案：

- **物理层（第一层）**：按年份归档，一级目录固定为 `YYYY`。
- **物理层（第二层）**：按「日期 + 主题」建目录，目录名即主题名，全局唯一。
- **逻辑层**：用本地数据库为每个主题、每张照片建立可检索的元数据记录（拍摄时间、设备、GPS、MD5、时长等）。

这套方案的特点是：**不依赖任何云服务、不改动原始文件、任何一款工具都能读懂**。即使 Photo World 被卸载，硬盘上的目录结构本身仍然是可读、可备份、可迁移的。数据库只是加速器，不是唯一真相（single source of truth 是文件本身）。

## 第 1 章 为什么照片必须被"归档"而不是"堆放"

### 1.1 三种常见失败状态

| 状态 | 表现 | 后果 | 能否事后补救 |
|---|---|---|---|
| **堆积** | `IMG_0001.jpg` 一万个躺在一个文件夹里 | 找不到任何一张，等于没有 | 极难，只能靠事后 EXIF 重建日期，主题信息永久丢失 |
| **重复** | 手机 + 相机 + 云盘各一份，多份拷贝互相覆盖 | 删错版本、版本混乱 | 中等，可靠 MD5 去重清理 |
| **失控** | 文件被移动/删除，索引失效 | 记忆里的照片再也调不出来 | 极难，索引需要重建，且丢失时间点不可知 |

### 1.2 归档的三个目标

一套合格的归档方案必须同时满足：

1. **可寻址（Findable）**——任意一张照片，30 秒内定位到文件。
2. **可解释（Self-describing）**——文件夹名本身说明内容，不依赖数据库也能读懂。
3. **可幸存（Durable）**——换设备、换软件、换硬盘格式，10 年后仍能打开。

第 2 点是最容易被忽略、也最关键的。本白皮书坚持「**目录名即语义**」，就是为了让文件系统本身具备自解释能力。

### 1.3 目录 vs 数据库的分工

| 层 | 载体 | 职责 | 丢失后果 |
|---|---|---|---|
| 物理层 | 硬盘目录树 | 保存原始文件 + 人可读语义 | 灾难性（文件本体） |
| 逻辑层 | `photo_world.db`（SQLite） | 多维索引、去重、GPS 检索、AI 描述 | 可重建（重扫一次即可） |

> **原则：文件是本体，数据库是索引。** 索引可以丢、可以错、可以删了重建；文件不行。

## 第 2 章 目录规范：两级结构

### 2.1 规范定义

照片库固定为**两层**，不多不少：

```
<库根>/                          例：D:\照片
└── YYYY/                        第一层：年份，固定 4 位数字
    └── YYYYMMDD主题/             第二层：日期 + 主题，例 20260101过年
        ├── IMG_0001.HEIC
        ├── IMG_0002.MOV
        └── ...
```

- 第一层目录名必须是 `YYYY`（`1900`–`2200` 之间的 4 位数字），用于**归档与年度重扫**。
- 第二层目录名 = `YYYYMMDD` + 分隔符（`-` / `_` / `·` / `.` / 空格，可省）+ **主题关键词**，该目录下的所有照片/视频都归属这个主题。
- 第二层目录名**就是主题名**，全库唯一，不允许两个不同事件用同一个目录名。

### 2.2 命名规则细则

| 规则 | 正例 | 反例 | 原因 |
|---|---|---|---|
| 主题名用事件而非泛词 | `20260217西湖`、`20250128过年` | `旅行`、`IMG2025`、`新建文件夹` | 泛词目录一年后无法检索 |
| 日期用事件发生日，非拍摄日 | `20250301体检`（当天检查） | 用导出/拷贝日期 | 语义正确 |
| 主题名 2–8 字，控制在单行 | `20251001国庆` | `20251001国庆第一天在西湖断桥人山人海` | 太长 Windows 路径易超 260 字符 |
| 不用标点分隔的多段语义 | `20260217西湖西湖-晚饭` | `20260217西湖/晚饭/`（再建子层） | 破坏两级结构 |
| 忌字符 `\ / : * ? " < > \|` | — | — | Windows 文件系统保留字符 |
| 同日多事件用序号区分 | `20260217西湖`、`20260217晚饭` | 两次事件共用一个目录 | 一目录一主题，不混装 |

### 2.3 主题名不剥离日期前缀（重要约定变更）

历史实现曾把 `20250128过年` 截成 `过年` 作为主题名。现行约定为：

- **`topic` = 文件夹全名**（即 `20250128过年`）；
- `event_date` = `2025-01-28`，仅由前缀解析，**仅用于年内排序**；
- 目录名不带日期前缀时（如 `旅行`），`topic` = 整名，`event_date` = 空。

这样处理的原因：目录名原样保留在磁盘上与数据库里**完全一致**，避免出现「盘上是 `20250128过年`、系统里显示 `过年`」的认知割裂；排序功能则交给独立的 `event_date` 字段承担，两者职责分离。

### 2.4 一目录一主题（重叠检测）

导入时必须做**父子/同级重叠检测**，三种结果：

| 情形 | 判定 | 处理 |
|---|---|---|
| 目标 = 已管理目录 | `exact` | 跳过，提示「已在库中」 |
| 目标 ⊂ 已管理目录 | `child` | 拒绝，防止重复入库导致归属错乱 |
| 目标 ⊃ 已管理目录 | `parent` | 拒绝，防止覆盖已有管理范围 |

原因：若同时管理 `D:\照片\2026` 与 `D:\照片\2026\20260101过年`，扫描同一文件时数据库的 upsert 会把 `folder_id` 改写成后扫的那个，导致父目录计数失真、媒体归属错乱。

## 第 3 章 导入流程

规范定好之后，日常操作只剩三步。

### 3.1 标准流程

```
① 解析      输入库根 D:\照片 或年份路径 D:\照片\2026 → 识别年份列表
② 列举      选中年份 → 列出该年所有主题目录（解析日期、统计文件数、标记是否已导入）
③ 导入扫描  勾选主题 → 批量入库并排队扫描 → 元数据写库
```

### 3.2 批量导入的工程约束

| 约束 | 原因 |
|---|---|
| **串行队列**（一次只扫 1 个目录） | 批量导入整年几十个目录时，并发扫描会把磁盘 IO 打满、SQLite 写入争用 |
| **递归扫描** | 主题目录下允许有子目录，扫描必须递归收集 |
| **读取失败必须记账** | 目录读失败（掉盘、权限变更、硬盘未挂载）要记为 error，**不能静默返回空数组**——否则会被上层误判为「目录已空」，把该目录全部文件标为丢失 |
| **增量跳过** | 以「文件修改时间 + 大小」判断未变更文件，重复扫描秒级完成 |
| **可中途取消** | 大目录扫描过程中用户要能停 |
| **容量上限** | 递归统计目录文件数设 20000 上限，避免超大目录卡住界面 |

### 3.3 老库迁移

约定变更（主题名不再截断）必须能平滑作用于既有数据库：

1. 启动时用 `PRAGMA table_info` 探测缺失列，`ALTER TABLE` 补齐 `year` / `topic` / `event_date` / `parent_path`；
2. **索引在迁移之后创建**——`schema.sql` 里不能引用尚未存在的列，否则老库启动即报错；
3. 启动时把既有记录的 `topic` 统一刷新为文件夹全名。

全程无需手工迁移，无需重扫。

## 第 4 章 元数据体系

目录只解决「找哪一批」，**要找到「哪一张」必须靠元数据**。

### 4.1 主题（folders）字段

| 字段 | 说明 | 示例 |
|---|---|---|
| `path` | 第二层目录绝对路径（唯一键） | `D:\照片\2026\20260101过年` |
| `alias` | 显示名 | `2026 / 20260101过年` |
| `year` | 第一层年份 | `2026` |
| `topic` | 主题 = 文件夹全名 | `20260101过年` |
| `event_date` | 由前缀解析的日期，仅用于排序 | `2026-01-01` |
| `parent_path` | 第一层年份目录 | `D:\照片\2026` |
| `image_count` / `video_count` / `livephoto_count` | 文件计数，导入后回填 | `128 / 12 / 5` |
| `scan_status` | `pending` / `scanning` / `done` / `failed` | `done` |

### 4.2 媒体（media）字段

每张照片/视频一行，共 37 个字段，核心分组：

| 分组 | 字段 |
|---|---|
| 身份 | `file_name`、`file_path`、`md5`、`file_size`、`mtime`、`format` |
| 时间 | `taken_at`、`taken_at_source`（`exif` / `ffprobe` / `file_mtime`） |
| 影像 | `width`、`height`、`megapixel`、`orientation`、`duration`、`codec` |
| 相机 | `camera_make`、`camera_model`、`lens_model`、`f_number`、`exposure_time`、`iso`、`focal_length` |
| 位置 | `gps_lat`、`gps_lon`、`gps_alt` |
| 状态 | `scan_status`、`is_missing`、`missing_since`、`is_livephoto`、`marked` |
| 原文 | `raw_metadata`（原始元数据 JSON 全文，列表查询禁止 SELECT 该列） |

**拍摄时间必须记录来源标记**：EXIF 缺失时回退到文件修改时间，但要标记为 `file_mtime`，否则排序结果会静默失真。

### 4.3 必须具备的检索维度

| 维度 | 用途 | 支撑字段 |
|---|---|---|
| 时间轴 | 按年月浏览、按拍摄时间排序 | `taken_at` |
| 场景 | 地图打点、找「去年在杭州拍的」 | `gps_lat/lon` |
| 设备 | 找出某个相机/手机拍的全部照片 | `camera_model` |
| 画质 | 筛出高像素、4K 视频 | `megapixel`、`duration` |
| 内容重复 | 找出同一张图的多个副本 | `md5` |
| 特殊标记 | 实况照片、已丢失、用户标记 | `is_livephoto`、`is_missing`、`marked` |

### 4.4 格式覆盖

| 类型 | 格式 | 依赖 |
|---|---|---|
| 图片 | JPG/JPEG、HEIC、WEBP、PNG、TIFF 等 | sharp（分辨率）+ exifr（EXIF/GPS）；HEIC 分辨率需 ffprobe |
| 视频 | MOV、MP4、AVI | ffprobe（时长/编码/GPS/设备） |
| 实况照片 | 同目录同文件名的 HEIC + MOV 配对 | 自动识别，标记 `is_livephoto` |

ffmpeg / ffprobe 路径由用户在设置页配置，缺失时**降级运行**（只取能拿到的字段），不阻塞整体流程。

## 第 5 章 维护操作

### 5.1 日常动线

| 场景 | 操作 |
|---|---|
| 拍了新照片 | 建 `2026/20260315主题/` → 拖入 → 导入页勾选该主题 → 扫描 |
| 换了新手机 | 导出后按日期+主题拆分到对应年份目录，再导入 |
| 找一张老照片 | 按年份 → 按主题浏览；或用媒体列表按拍摄时间/设备/地图筛选 |
| 定位到具体照片 | 详情弹窗看 37 个字段；带坐标可一键跳地图 |
| 判断是否重复 | 重复检测页（按 MD5，视频可参与） |
| 源文件被删 | 记录保留并标 `is_missing` + 记录丢失时间，可追溯 |

### 5.2 移除主题的语义

移除某个主题（第二层目录）时，其媒体记录与扫描任务**一并从数据库清理**，但**磁盘文件不受影响**。这是一个重要的安全属性：管理操作永远不会动你的原始文件。

## 第 6 章 备份与长期保存

目录规范解决「整理」，但真正决定照片能否幸存 10 年的是备份。

### 6.1 3-2-1 原则

| 条目 | 要求 |
|---|---|
| 3 份副本 | 原始盘 + 本地备份盘 + 异地/云端 |
| 2 种介质 | 至少一块物理盘 + 一份云端或离线盘 |
| 1 份异地 | 不在同一房间/同一栋楼，防火防盗灾 |

### 6.2 增量备份而非全量拷贝

按目录树整体拷贝，10 万张照片意味着每次全量。

- 用工具的**修改时间 + 大小**判断变更，只传新文件；
- 数据库（`.db` / `.db-shm` / `.db-wal`）一并备份，但它可重建，优先级最低；
- 备份目标是**保住目录树 + 文件本体**，元数据丢了重扫一次就有。

### 6.3 长期保存的格式建议

| 存储形态 | 保存年限 | 说明 |
|---|---|---|
| JPEG / HEIC（原始） | 长期 | 保留原始质量，不做有损压缩 |
| 归档级转码（如 JPEG XL / TIFF） | 30 年+ | 关键照片（证件、孩子第一张）建议额外做一份归档格式 |
| 缩略图 / 预览 | 随时可重建 | **不要**手工备份，丢了重扫即得 |
| 云相册 | 非归档 | 仅作分享与检索用途，不作为唯一副本 |

> 缩略图、索引、AI 描述这些「派生数据」都可以重建。**唯一不可再生的是原始文件本身。**

## 第 7 章 进阶：AI 照片描述

目录与元数据解决「结构化检索」，但「去年在西湖拍的那张有船的照片」这类**内容检索**需要 AI 描述。

### 7.1 设计原则：与扫描彻底解耦

AI 分析**不内联进扫描流程**，作为独立阶段：

```
扫描阶段（已有）→ media 表（每行 ai_desc_status='pending'）
                        │ 用户触发 / 定时
                        ▼
        AI 分析引擎（仿扫描模式：并发池 + 可取消 + 进度表）
          ffmpeg 抽帧 → sharp 缩放 → 视觉模型 → 写库
                        ▼
        media.ai_desc / ai_desc_model / ai_desc_at
                        ▼
        详情展示 / 列表筛选 /（进阶）FTS 内容搜索
```

理由：扫描是纯元数据提取，快且稳定；AI 慢、贵、受限流影响。混在一起会让扫描被拖垮、失败难以重试。

### 7.2 模型选型

| Provider | 推荐模型 | 视觉能力 | 成本（约/千张） | 数据出境 | 备注 |
|---|---|---|---|---|---|
| **OpenAI** | gpt-4o-mini | 强 | $2~3 | 美国合规 | 性价比首选 |
| OpenAI | gpt-4o | 最强 | $10~15 | 美国合规 | 描述质量要求高时用 |
| **Google** | gemini-1.5-flash | 强 | 极低/有免费额度 | 美国合规 | 推荐 |
| Anthropic | claude-3.5-haiku | 强 | 中 | 美国合规 | |
| **本地** | Ollama + llava / qwen2-vl | 中 | 0（算力成本） | **零出境** | 需 GPU；隐私最强 |

隐私敏感的照片走本地方案，彻底不出本机。1 万张的量级：gpt-4o-mini 约 $20~30，Gemini Flash 更低。

### 7.3 增量与重跑

- **增量**：只对 `ai_desc_status` 为 `pending` / `failed` 的记录跑，不重复烧钱；
- **改 prompt 重跑**：`ai_prompt_ver + 1`，批量重跑旧版本记录；
- **取消**：与扫描同一套机制（轮询 `cancelled` 标志）。

## 第 8 章 实施清单

按顺序执行，每步都有明确产出：

| # | 步骤 | 产出 / 验收标准 |
|---|---|---|
| 1 | 建立库根目录，如 `D:\照片` | 存在空目录 |
| 2 | 建第一层年份目录 | `2024` `2025` `2026` |
| 3 | 按「日期 + 主题」建第二层目录 | 目录名合规、无保留字符、语义具体 |
| 4 | 把已有照片归位到对应主题目录 | 无散落在年份目录根部的照片 |
| 5 | 配置 ffmpeg / ffprobe 路径（设置页） | 视频/HEIC 能解析出完整字段 |
| 6 | 导入 → 解析路径 → 选年份 → 勾选主题 → 扫描 | 主题列表显示文件数与「已导入」状态 |
| 7 | 抽查校验 | 随机抽 10 张：拍摄时间、相机型号、GPS 是否正确 |
| 8 | 建备份 | 3 份副本、2 种介质、1 份异地 |
| 9 | 设置增量备份 | 新增照片自动上传，不需人工介入 |
| 10 | （可选）开启 AI 描述 | 详情页出现自然语言描述 |

### 快速自检（十条对照）

1. 一级目录是否全部为 4 位年份？
2. 二级目录是否都是「日期 + 具体主题」？
3. 主题名里有没有 `旅行`、`新建文件夹`、`未分类` 这类泛词？
4. 目录名有没有 Windows 保留字符？
5. 有没有同一事件被拆进两个目录？
6. 有没有把两个事件混装进一个目录？
7. 是否存在「有文件但没导入系统」的主题目录？
8. 拍摄时间来源是否都是 `exif`（而非大面积 `file_mtime`）？
9. 是否有 3 份副本？
10. 随机抽 10 张，能否在 30 秒内从磁盘定位到？

## 附录 A 名词表

| 术语 | 定义 |
|---|---|
| **库根** | 照片库的顶层目录，如 `D:\照片`，其下一级必须是年份目录 |
| **年份层** | 第一层目录，命名 `YYYY`，用于归档与整年重扫 |
| **主题（topic）** | 第二层目录，命名 `YYYYMMDD + 主题词`，一个目录 = 一个主题 |
| **主题目录** | 同上，即受管理文件夹（`folders` 表一行） |
| **事件日期（event_date）** | 由主题目录名前缀 `YYYYMMDD` 解析出的日期，仅用于排序 |
| **媒体（media）** | 主题目录下的一张照片或一个视频 |
| **实况照片** | 同目录同文件名的 HEIC + MOV 配对，iPhone 拍摄产物 |
| **串行队列** | 扫描任务排队逐个执行，同时最多 1 个在跑 |
